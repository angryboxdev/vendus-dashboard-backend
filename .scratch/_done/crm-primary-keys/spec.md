## Problem Statement

Five tables in the CRM module have a **business-key primary key with no
organization in it**: `crm_customers.id` (`'C001'`, `'C002'`, ...),
`crm_parameters.key`, `crm_scripts.code`, `crm_tags.name`, and
`crm_action_types.code` — a fifth table with the identical shape that the
original deferred-item register (org-location-foundation spec, "Table
inventory") never named, because it wasn't in that spec's table list either
(see that migration's own header note: `crm_action_types` and
`crm_customer_actions` are two of the four tables missing from spec A's
inventory prose, added anyway because the schema pass's rule was
unconditional). All five already carry `org_id NOT NULL` (added in
`20260822150000_tenancy_schema_pass.sql`), but the primary key itself is
still the bare text column, globally unique across every organization that
will ever exist.

**The moment a second organization creates its first customer, parameter,
script, tag, or action type reusing a value the first organization already
has, the insert fails a unique-constraint violation.** This is not a
tail-risk edge case — it is closer to a certainty, because these are exactly
the values two independent restaurants are likely to pick the same way:

- `crm_customers.id` is not user-chosen at all. It's generated by
  `nextCustomerId()`
  (`src/services/crmCustomerService.ts:83-93`), which already queries
  scoped by `organizationId` and always starts a fresh organization at
  `'C001'`:

  ```ts
  async function nextCustomerId(organizationId: OrganizationId): Promise<string> {
    const { data } = await createScopedQuery(organizationId)
      .table("crm_customers")
      .select("id")
      .order("id", { ascending: false })
      .limit(1)
      .single();

    if (!data) return "C001";
    ...
  }
  ```

  The application layer already behaves as if customer numbering were
  per-organization — it has since spec B2 threaded `organizationId` through
  every call site. **The bug is that the schema has not caught up to what the
  application already assumes.** Organization #2's very first customer will
  be assigned `'C001'` by this exact code path and rejected by the database,
  because organization #1 already has one.
- `crm_tags.name`, `crm_scripts.code` and `crm_action_types.code` are
  human-chosen labels from a small, predictable vocabulary — `'VIP'`,
  `'2.1.1'`, `'follow-up'` — that any two restaurants configuring their CRM
  from scratch are likely to converge on independently, with nothing today
  reseeding per-organization defaults but every reason to expect an
  onboarding flow will want to eventually (see "Noted, not decided" below).
- `crm_parameters.key` is a config key (`'reminder_days'`-style); the same
  reasoning applies once a second organization needs its own copy of a
  parameter the first organization already defined.

**This is a correctness/availability bug at onboarding time, not a security
fix — the opposite motivation from the sibling composite-FK spec.** The
composite-FK spec (item 1 of the original six) exists because an unvalidated
foreign key lets one organization's write silently reference another
organization's row — a hole a security review would eventually find, because
nothing crashes and no user notices. This item is the reverse: nothing is
unsafe while it sits broken, and nothing a security audit greps for would
flag it. It fails the instant it is exercised, loudly, as a `23505
unique_violation` on the CRM's most basic write path (create customer, add a
tag, configure a script) at the exact moment a second organization is
provisioned — which is also the one moment onboarding cannot afford a crash.
The original deferred-item register named this precisely: *"the item most
likely to be forgotten, because unlike the others it fails loudly at
onboarding rather than silently."* It is forgettable for the same reason it
is safe to defer: with one organization, `'C001'` can never collide with
anything, so there is nothing to see in the running system today — the risk
is entirely in the future, on a code path (org #2 provisioning) that doesn't
exist yet either.

## Current schema (verified against `supabase/migrations`, not the archived
`_archive/048_crm_tables.sql` prose, which predates `org_id`)

| Table | Primary key today | `org_id` | Notes |
|---|---|---|---|
| `crm_customers` | `id text` | `NOT NULL` (no default; dropped in `20260831152632`) | Self-referencing FK: `referred_by text references crm_customers(id)` |
| `crm_parameters` | `key text` | `NOT NULL` | No dependents — nothing in `src/` or the schema references `crm_parameters.key` as a foreign key |
| `crm_scripts` | `code text` | `NOT NULL` | No *enforced* dependents — see D5 |
| `crm_tags` | `name text` | `NOT NULL` | Dependent: `crm_customer_tags.tag_name` |
| `crm_action_types` | `code text` | `NOT NULL` | Dependent: `crm_customer_actions.action_type_code`. Queried through the new-pattern module (`src/modules/crm/adapters/out/supabase-crm-workspace.repository.ts`), not just the legacy service layer |

Dependent (child) tables and their current FKs to the five above:

| Table | FK column(s) → parent | Current constraint | This spec's fix |
|---|---|---|---|
| `crm_contacts` | `customer_id text` → `crm_customers.id` | `crm_contacts_customer_id_fkey` (single-column) | composite `(org_id, customer_id)` → `crm_customers(org_id, id)` |
| `crm_orders` | `customer_id text` → `crm_customers.id` | `crm_orders_customer_id_fkey` (single-column) | composite `(org_id, customer_id)` → `crm_customers(org_id, id)` |
| `crm_customer_tags` | `customer_id text` → `crm_customers.id`; `tag_name text` → `crm_tags.name` | two single-column FKs; PK is `(customer_id, tag_name)` | composite FKs on both, **and the join table's own PK must gain `org_id`** — see D3 |
| `crm_customer_actions` | `customer_id text` → `crm_customers.id`; `action_type_code text` → `crm_action_types.code` | two single-column FKs | composite FKs on both — **a fourth dependent table, not named in the original three-table framing** (see D4) |
| `crm_customers.referred_by` | `referred_by text` → `crm_customers.id` (self) | single-column FK | composite `(org_id, referred_by)` → `crm_customers(org_id, id)` |

Two columns look like they should be dependents and are not, today:
`crm_contacts.script_code` and `crm_customer_actions.script_code` are plain
`text`, with **no foreign key constraint** to `crm_scripts.code` at all. See
D5 — this spec does not add one.

## Solution

**Composite primary keys, not surrogate keys.** Each of the five tables
keeps its existing text column and gains `org_id` as a co-equal part of the
primary key: `crm_customers` becomes `primary key (org_id, id)`, and likewise
for `crm_parameters (org_id, key)`, `crm_scripts (org_id, code)`, `crm_tags
(org_id, name)`, `crm_action_types (org_id, code)`. Every dependent table's
foreign key becomes the matching composite `(org_id, <fk column>)` →
`(org_id, <parent pk column>)`, following the exact pattern
`docs/adr/0009` used for the location composite keys and whatever the
sibling composite-FK spec formalizes for the remaining ~65 (see D1, D6).

This is a schema-only change. No application code needs to change how it
generates or looks up these ids: `nextCustomerId()` and every other read/write
site already goes through `createScopedQuery(organizationId)` /
`scopedQuery(organizationId)` (spec B2's helper), which already filters every
query by `org_id` (`src/infra/scoped-db/table-registry.ts` already lists
`organizationColumn: "org_id"` for all five tables and their dependents).
The bug being fixed is purely that the *constraint* has not caught up to
what every call site already assumes — see D8.

### What this spec deliberately is not

- Not a surrogate-key migration (rejected — see D1).
- Not the composite-FK spec itself. That spec covers the ~65 pre-existing FK
  references across the whole schema; this spec covers exactly the ones
  listed above, and inherits that spec's technique rather than choosing its
  own (D6).
- Not a fix for the two unenforced `script_code` columns (D5), the kiosk PIN
  item, or storage path prefixing — those are separate deferred-register
  items.
- Not a per-organization CRM seeding feature (default tags, scripts, action
  types for a newly onboarded organization). That doesn't exist today for
  any organization and is out of scope here; this spec only makes it *safe*
  for such a feature to reuse values across organizations once someone
  builds it (see "Noted, not decided").

## Implementation Decisions

### D1 — Composite primary key, not a surrogate `uuid` key

Two shapes were available: widen the existing text PK to `(org_id, id)`, or
add a new surrogate `uuid` primary key and demote the text value to an
`unique (org_id, <business key>)` constraint (the shape `locations` actually
uses — `id uuid primary key`, `unique (org_id, code)`).

**Composite PK wins here, for a reason that doesn't apply to `locations`:**
`crm_customers.id` is a **live, public API path parameter** —
`GET/PATCH /crm/customers/:id` (`src/routes/crmRoutes.ts:83,93` and three
more routes) — read and written by the frontend as the text value `'C001'`.
A surrogate-key migration would replace what the frontend sends and
receives on every one of those routes, which is exactly the kind of change
the original deferred-item register flagged as needing a frontend contract
change for a *different* item (the kiosk PIN fix) and deliberately avoided
for this one. Composite PK requires no such change: `'C001'` keeps meaning
exactly what it means today, scoped correctly for the first time.

The `locations` precedent doesn't transfer directly for the same reason in
reverse: `locations.id` was already a server-generated `uuid`, never
human-facing, so giving it a surrogate key cost nothing and a composite PK
would have gained nothing (a `uuid` cannot collide across organizations
regardless of scoping). The CRM tables' text values are the opposite case —
human-facing, and per-organization-meaningful by design (evidenced by
`nextCustomerId()` already resetting to `'C001'` per organization) — so the
composite PK is not a compromise here, it's the shape the application
already wanted.

### D2 — `crm_action_types` is in scope, correcting the four-table framing

The handoff and the original deferred-item register both name four tables
(`crm_customers`, `crm_parameters`, `crm_scripts`, `crm_tags`).
`crm_action_types.code` has the identical shape — `text primary key`, no
`org_id` in the key, referenced by a dependent table's FK
(`crm_customer_actions.action_type_code`) — and is exercised through the
new-pattern CRM module's action-type CRUD
(`supabase-crm-workspace.repository.ts:54-64`), not just legacy code. It
was missing from spec A's own table inventory for the same reason four other
tables were (see `20260822150000_tenancy_schema_pass.sql`'s header note) —
an inventory compiled from docs, not the live schema. It is added to this
spec's scope on the same unconditional basis that migration used: it is a
real table with a real dependent, so it gets the same fix as its four
siblings.

### D3 — The join table's own primary key needs `org_id`, not just its FKs

`crm_customer_tags` is a dependent of both `crm_customers` and `crm_tags`,
but it is not *only* a dependent — its own primary key, `(customer_id,
tag_name)`, has the same collision shape as its parents' keys. Once two
organizations can each have a customer `'C001'` and a tag `'VIP'`, a plain
`(customer_id, tag_name)` primary key collides the moment both organizations
tag their respective `'C001'` as `'VIP'` — a second, independent collision
sitting one level down from the one this spec is nominally about. The fix
is the same shape: the primary key becomes `(org_id, customer_id, tag_name)`,
in addition to the two composite foreign keys.

`crm_customer_actions` does not have this problem — its own primary key is
`id uuid`, generated server-side, so only its foreign keys need widening.

### D4 — `crm_customer_actions` is a fourth dependent table, correcting the three-table framing

The handoff names three dependent tables (`crm_contacts`, `crm_orders`,
`crm_customer_tags`). `crm_customer_actions` has two foreign keys into the
tables this spec restructures (`customer_id` → `crm_customers`,
`action_type_code` → `crm_action_types`) and needs the same composite-FK
treatment as the other three. Added to scope for the same reason as D2: it
is a real, currently-enforced FK relationship into a table this spec
changes the key shape of, not a hypothetical one.

### D5 — `script_code` stays unenforced; this spec does not add a new foreign key

`crm_contacts.script_code` and `crm_customer_actions.script_code` are plain
`text` columns with **no foreign key constraint** to `crm_scripts.code`
today — confirmed by grep across every migration file, only five CRM
foreign keys exist in the schema and neither of these two columns is one of
them. Adding composite FK enforcement here would be a new constraint the
system has never had, not a restoration of one this spec's `org_id` work
displaced — a different, additive piece of work with its own risk (existing
rows with a `script_code` that doesn't match any `crm_scripts.code`, e.g.
`'free'` per the original archived seed comments, would need handling before
such a constraint could validate). Left as a follow-up, not blocking this
spec or the gate: the gate's requirement is that a business-key primary key
does not collide across organizations, which these two columns' current,
unenforced state cannot violate.

### D6 — The migration technique is inherited from the composite-FK spec, not chosen independently

Two techniques exist in this repository's own history for adding a
composite foreign key: `docs/adr/0009`'s reasoning (via
`org-location-foundation/spec.md` D8) describes the fully-online path —
`CREATE UNIQUE INDEX CONCURRENTLY`, then the FK as `NOT VALID` followed by
`VALIDATE CONSTRAINT` (`SHARE UPDATE EXCLUSIVE`, no long lock) — but the
migration that actually shipped the five location composite keys
(`20260831152632_drop_defaults_and_location_composite_keys.sql`) used a
plain synchronous `ADD CONSTRAINT` for both the unique constraint and every
FK, evidently judged safe given the tables' size and the one-organization
window.

This spec does not re-decide which of those two is correct for the CRM
tables. The composite-FK spec (`.scratch/composite-fk-indexes/`, gate item
1) is expected to settle the standard technique for the ~65 remaining
pre-existing FK references it covers, and this spec's five tables and four
dependents reuse whatever it settles on, for consistency and because that
spec is better positioned to judge current production row counts than this
one. The CRM tables are, on their face, low-cardinality operational tables
in the same rough class as `locations` (customers, tags, scripts, parameters
and action types are all human-curated, not event-grain data), which is a
point in favor of the simpler synchronous path being sufficient again — but
that is this spec flagging a hint for whoever writes the actual migration
ticket, not a decision made here.

### D7 — Sequencing: design now, implement after the hard dependency lands

This spec exists to make the scope, the table list, and the reasoning
explicit *before* the composite-FK spec is written, so that whoever writes
that spec knows a second, dependent piece of work is waiting on it, and so
the CRM-specific analysis (D1–D5) doesn't have to be redone later under time
pressure. Concretely:

- Writing tickets from this spec, and picking any of them up, is blocked
  until `.scratch/composite-fk-indexes/spec.md` exists **and its own FK work
  has merged** — not merely been written. Re-check both before starting.
- If `.scratch/composite-fk-indexes/` does not yet exist when this spec is
  next read, that is expected, not a sign this spec is out of date — see
  the header note.
- Nothing here needs to change once that spec lands, unless it settles on a
  materially different composite-FK shape than `(org_id, <fk column(s)>)` →
  `(org_id, <parent pk column(s)>)`, which would be a surprise given
  `docs/adr/0009` already establishes that shape as precedent.

### D8 — Why the application layer needs no changes

Spec B2 (`scoped-access`) already made `org_id` an explicit, typed parameter
threaded through every output port and legacy service function for these
tables, and the scoped query helper (`ADR-0008`) already filters every
`select`, stamps every `insert`, and scopes every `update`/`delete` by
`org_id` for any table in its registry — which already includes all five
tables and all four dependents (`src/infra/scoped-db/table-registry.ts:79-90`
approx.). The bug this spec fixes lives entirely in the database's
constraint layer, not in any query the application builds. This is why
`nextCustomerId()` (Problem Statement) is presented as evidence rather than
as something to fix — it is already correct, and is exhibit A for what the
schema is failing to honor today.

## Testing Decisions

Per this repo's testing conventions, and D11 of the org-location-foundation
spec (no existing test touches the schema — all 136+ test files use fakes
for output ports): verification here is migration-level, not unit-level.

- **Two-organization insert test** (smoke test against the local stack, not
  a unit test): create two organizations, each creates a customer with the
  same generated id (`'C001'`), the same tag name, the same script code,
  the same parameter key, and the same action-type code — every insert
  succeeds.
- **Cross-organization reference is rejected**: attempt to insert a
  `crm_contacts` / `crm_orders` / `crm_customer_tags` / `crm_customer_actions`
  row for organization A's `org_id` naming organization B's customer/tag/
  action-type id — the composite FK rejects it.
- **`crm_customer_tags`'s own composite PK** (D3): the same `(customer_id,
  tag_name)` pair under two different organizations both insert
  successfully; the same triple `(org_id, customer_id, tag_name)` twice
  under the same organization still fails as a duplicate.
- Existing single-organization behavior is unchanged: the current
  Angrybox data must migrate cleanly (every existing row's `org_id` is
  already the seeded Angrybox org from `20260822150000_tenancy_schema_pass.sql`,
  so no backfill is needed — this is the same "the default made backfill a
  no-op" situation D2 of the org-location-foundation spec already relied on).

## Out of Scope

- The composite-FK spec itself and its ~65 other FK references
  (`.scratch/composite-fk-indexes/`).
- Enforcing a foreign key on `crm_contacts.script_code` /
  `crm_customer_actions.script_code` (D5).
- Kiosk PIN scoping and storage path org-prefixing — the two other still-open
  gate items, unrelated to the CRM tables.
- Any per-organization CRM seeding/defaults feature (see "Noted, not
  decided").
- Frontend changes. `crm_customers.id` stays a text value with the same
  shape and the same meaning; no route, request or response shape changes
  (this is the point of D1).

## Further Notes

### Deferred register

This closes gate item 4 as originally listed in
`.scratch/_done/org-location-foundation/spec.md`'s "Deferred to spec B"
table, once implemented — with the scope corrected to five parent tables
and four dependents (D2, D4), not four and three. The gate remains: **no
second `organizations` row until every deferred item is done**, and after
this spec, composite-FK indexes (item 1, in progress as its own spec), the
kiosk PIN fix (item 5) and storage path org-prefixing (item 6) are the
ones still open.

### Risks

- **Sequencing risk is the main one.** If a ticket from this spec is picked
  up before the composite-FK spec's technique is settled, the CRM migration
  either invents its own technique (risking inconsistency with the other 65
  FKs) or blocks mid-flight. D7 exists to make this failure mode explicit
  rather than discovered during implementation.
- **`crm_customer_tags`'s PK widening (D3) is easy to miss** — it reads like
  "just add composite FKs to a join table" until the join table's *own*
  primary key is examined. Flagged prominently (D3) so a future
  implementer doesn't ship half this spec.
- Low risk otherwise: no application code changes, no frontend contract
  change, small/low-cardinality tables, and the existing single-organization
  data requires no backfill (org_id is already populated everywhere).

### Noted, not decided

- **Per-organization CRM defaults.** Nothing in the repository today seeds a
  new organization's `crm_tags`, `crm_scripts`, `crm_action_types` or
  `crm_parameters` — the archived `_archive/049-051_crm_seed_*.sql` files
  seeded Angrybox once, by hand, and there is no onboarding pipeline yet
  that would run something equivalent for organization #2. This spec makes
  it *safe* for such a pipeline to reuse the same default values (`'VIP'`,
  `'reminder_days'`, etc.) across organizations; it does not build the
  pipeline. Worth flagging to whoever eventually specs organization
  onboarding.
- **`crm_customer_actions.source_key`** carries a global `unique` constraint
  (`crm_customer_actions_source_key_key`) that was not touched by the
  tenancy schema pass and has no `org_id` prefix. Nothing in `src/` writes
  or reads this column (grep across `src/` returns no hits), so it may be
  dead. Not this spec's problem — it isn't one of the five business-key
  primary keys and isn't a dependent's foreign key — but worth a quick look
  by whoever next touches `crm_customer_actions`, since it has the same
  collision shape as everything else in this document.
- **`crm_customer_actions.source_contact_id`** also carries a global unique
  constraint, but it references `crm_contacts.id`, which is a server-generated
  `uuid` — not a business key, so it cannot collide across organizations
  regardless of scoping. No action needed.
